# 0004 — 手牌對帳：讓「畫面上的手牌是錯的」不可能靜默存在

狀態：完成（2026-09-22）
開工：2026-09-22

## 目標

一句話：手牌不再寄生在房間那一列的 `rev` 上，而且只要它錯了就會被自己抓到並修回來。

## 症狀

Francis 2026-09-22 回報：**線上多人、平面牌桌，叫完墩（骰子出完）手牌的牌面就換掉了。**

## 病灶（查過）

伺服器在同一局（同一個 `ri`）裡不會改任何人的手牌——手牌只有三個寫入點：
`deal()`（一定 `ri++`）、`writeHand()`（出牌）、同時叫墩寫 `hands.bid`（不碰 `cards`）。
所以「叫墩把牌換掉」不存在；真正發生的是**叫墩那一趟把畫面上一直是錯的牌校正成真的**。
自己按下叫墩的那一趟 `api("bid")` 回來的 `rev` 必定最新、必定通過 `fresher()`，
所以它是最穩定的一次校正機會——症狀才會固定出現在那一刻。

錯的牌能活那麼久，是因為這條路上每一環都靜默失敗：

| 環節 | 失敗時 | 有人發現嗎 |
|---|---|---|
| `fresher()` 擋掉一列 → 那一趟的 `hand` 一起被丟（`docs/index.html:3905`） | 手牌沒更新 | 沒有 |
| `needHand` 補的 `api("state")` 在 `BG` 名單裡，通道忙就靜默跳過（`3775`） | 補不回來 | 沒有 |
| `MYHAND_RI === row.ri` 但那其實是別場／別桌的同號局 | 沿用舊牌 | 沒有 |
| 非 ticker 的人在 bid 階段不敲 tick（`3750`） | 十秒內沒有任何帶手牌的請求 | 沒有 |

只修第一列，其餘三列照樣能產生一模一樣的症狀 —— 所以要的是對帳，不是補洞。

## 步驟

- [x] 0. trace 指紋：收到手牌、手牌被丟掉、對帳失敗各記一行（驗收證據）
- [x] A. 手牌有自己的身分：`MYHAND_KEY = code:match:ri` 取代 `MYHAND_RI`；
      換局／換場／換桌的手牌在 `fresher()` **之前**就收下（`rev` 只排同一局裡的先後，排不了跨局）
- [x] B. 對帳：`MYHAND.length` 必須等於 `hs - played - (我這墩出過?1:0)`（跟 `handCount()` 同一個公式，
      不需要任何私有資料）。對不上就重抓，帶指數退避
- [x] C. 修手牌那一趟不可以被丟掉：`api()` 加 `force`，繞過 `BG` 規則；`needHand` 那條也改用它
- [x] D. `scripts/net_test.ts` 補時序測試
- [x] E. `agent/PROGRESS.md`、本檔狀態

## 不做什麼

- 不動 Edge Function、不動 migration。`match`／`ri` 已經在每一列裡，客端自己就判得出來，
  上線只要 push 一次網頁（少一個部署風險）。
- 不做「realtime 推私有手牌」：要動資料表權限與訂閱結構，而且推播照樣會漏，
  最後還是需要 B 那道對帳。B 繞不過，先做 B 就好。
