# 11 Up & Down

叫墩撲克。局數從每人 1 張爬到 11 張再降回 1 張，共 21 局；每局翻一張王牌，
用骰子宣告自己會贏幾墩，叫中才有分。

- **玩**：https://we-do-stuff-tw.github.io/11-up-and-down/
- **計分**：叫 0 中得 5 分，叫 n 中得 10+n；沒叫中扣 |實際 − 叫的| 分。
- **牌組**：預設兩副 7–A 共 64 張。4 人要走完 1→11→1 至少需要 45 張。
- **牌桌**：右上角可切「平面／立體」，選擇記在 localStorage。

## 結構

```

supabase/functions/game/       牌局伺服器：發牌、驗證出牌、AI
```

## 立體牌桌

立體版把牌桌換成一張 WebGL 畫布（three.js 由 CDN 載入），其餘一切不變——
規則引擎、連線層、計分表、規則說明都是同一份程式碼。3D 是加上去的一層呈現，不是另一套實作。

- **載不起來就沒事發生。** three.js 抓不到、或裝置沒有 WebGL，這一層就不啟動，平面牌桌照常運作。
  兩層之間只有一個接縫：`window.UD`。引擎那邊不知道有 3D 這回事。
- **文字仍然是 DOM。** 座位名、骰子、分數、狀態列疊在畫布上，位置由 3D 座標投影出來。
  向量字因此保持清晰，鍵盤與螢幕閱讀器也不會失去入口。
- **手牌有兩層。** 3D 負責畫，DOM 留下一層透明但可對焦的按鈕，貼在投影後的牌面上，
  所以 Tab 的焦點框會落在正確的那張牌上；滑鼠與觸控走畫布的射線命中。
  「這張能不能出」只判斷一次——就是那顆按鈕的 `disabled`，3D 的明暗與浮起跟著它，規則不會有第二份。
- **牌面是貼圖。** `drawFace()` 用 canvas 依平面版 `cardFace()` 同一套版面（viewBox 0 0 100 140）
  重畫成一張圖集，整副牌只上傳一次紋理。**改牌面時兩邊要一起改。**
- **同步是宣告式的。** `sync()` 只算「現在桌上應該有哪些牌、各自該在哪」，再讓場景收斂過去；
  誰要飛、飛多久是位置變了才產生的結果，不是一段段動畫腳本。所以狀態跳著來
  （連線延遲、對手秒出、重新整理）不會有牌卡在半路。
- **取景是算出來的。** 桌上真的有東西的地方各出一組點，用真正的透視反推鏡頭距離再重新對中——
  手牌離鏡頭比對面那半張桌子近了快一半，用平行投影估會低估它放大多少，下緣就會被切掉。
- **直式螢幕把桌子壓成橢圓。** 圓桌配上手機的畫面比例，怎麼取景都會有一邊留下大片空桌。
  壓扁的是位置，不是牌。

## 手牌為什麼藏得住

發牌在 edge function 裡發生，手牌寫進 `hands` 表。那張表 RLS 開著、**一條 policy 都沒有**，
所以任何拿著 anon key 的瀏覽器都讀不到——包含房主的。每個人只會在自己的 API 回應裡
收到自己那份。`rooms` 表是公開狀態（檯面上的牌、叫墩、分數），本來就該所有人看得到，
但同樣沒有寫入 policy：牌局只能透過 edge function 推進。

身分不用 Supabase Auth，是一個存在 localStorage 的隨機 token，伺服器只留 sha256。
所以有連結就能玩，不用註冊。
